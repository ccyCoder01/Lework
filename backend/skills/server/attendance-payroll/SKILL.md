# 考勤核对

## 阶段路由

进入或跨越以下阶段时，先用 `scripts/workflow_gate.py` 检查当前任务的阶段证据和用户消息序列。只把对话中真实可见的用户原文及现有文件/回执摘要交给检查器；请求须带当前 `attendance.json` 路径，检查器自行计算其 SHA-256，并与 Review 摘要、版本及其在对话中展示后的用户消息序号核对。考勤确认记录必须回指同一任务中的明确确认消息，并与当前 Review 的月份、版本、摘要及人员范围完全一致；更正或重新生成 Review 后摘要/版本改变，必须重新确认。不得自造 `authorized=true` 或阶段成功记录。`ok=true` 仅表示符合正常 Skill 流程的准入条件，不是授权凭证，也不是 Runtime 强制权限。检查结果中的 `message_source_verified=false` 和 `runtime_enforced=false` 始终成立；文件路径与消息文本仍由 Skill 提供，写操作前 Agent 必须直接核对当前对话中的原始用户表达。无法确认消息来源或范围时停止。

阶段停顿规则：首次请求只完成考勤识别、核对表生成和 Artifact 声明，然后停止；用户确认考勤后，仅在当前任务原始指令明确要求时继续身份匹配及只读历史工资覆盖检查。进入一次性执行授权前，`workflow_gate.py` 必须从固定内部路径 `.attendance-work/payroll-readiness.json` 读取实际报告，并调用 `payroll_readiness.report_status()` 对照当前考勤、人员映射、月份及已选范围；报告状态、逐人明细、计数、规范化响应摘要和默认可核算范围还须与门禁请求一致。报告缺失、不可用、损坏、过期或冲突均停止。正式提交前仍须重新调用只读覆盖 MCP 并完成批次与范围复核。

完成映射与覆盖核验后，展示唯一默认可核算范围、排除原因及后续将执行正式考勤提交、正式 Precheck 和工资核算，再停止等待用户一次明确的工资核算执行授权。授权通过后，同一授权仅可按顺序用于该精确范围的提交、Precheck 和核算；提交回执、`valid=true` Precheck、批次及范围校验仍逐阶段必需。用户授权若表达增加、排除或替换人员等范围调整，不得按旧范围执行；先重新匹配、检查覆盖并展示新范围，再取得一次新的执行授权，不新增授权阶段。输入摘要、映射、覆盖结果、月份、人员集合或批次变化均使授权失效。

考勤事实确认、身份/覆盖核验、执行范围展示与一次性工资核算执行授权各自有不同含义。只有在唯一范围已展示并明确说明将正式提交考勤、执行正式预检查、再进行工资核算后，用户明确表示按该范围开始工资核算，才进入一次性执行路径。`确认考勤`、人员匹配完成、覆盖检查通过、`继续处理`、`查看工资表` 或“可以核算吗”均不构成该授权；不得从含糊或否定表达推断授权。授权消息中如提出增加、排除或替换人员，必须停止并重新核定、展示范围。范围或证据改变后必须重新检查并展示。只要求生成考勤确认表的任务不得调用任何 Payroll MCP。覆盖报告的本地一致性复核不认证原始 MCP 响应的远端来源，也不认证用户消息；`ok=true` 不代表正式 Precheck 通过或远端数据未变化。

1. **上传与识别**：新任务首次进入时读取 [recognition.md](references/recognition.md)，按下面九步执行。每个 PDF 只做一次确定性预处理；每页至多读取一次布局概览和每个固定数据分区，不能临时增图或补认。预处理可对轻微整体倾斜执行有界自动纠偏，不得将纠偏结果描述为修复透视或局部变形。逐页观察后立即保存，并按人员行号绑定印刷汇总及备注。
2. **自然语言核对与修改**：用户要求查看、修改或确认考勤时读取 [attendance-review.md](references/attendance-review.md)。Agent 将明确的自然语言更正转成脚本 JSON 请求；目标或事实有歧义时只询问必要问题。每次修改后重新检查、导出最新核对表并重新声明该文件。
3. **人员身份匹配**：仅当当前任务原始用户指令明确要求“考勤确认后匹配”且用户已确认考勤，或用户当前明确要求匹配时，读取 [identity-matching.md](references/identity-matching.md)。只调用 Payroll 的 `list_roster` 和 `resolve_payroll_person_candidates` 只读工具，并用 `scripts/person_matches.py` 构建或确认当前任务的身份映射。脚本先用姓名与显式规范项目筛查当前有效花名册，再要求候选响应明确证明唯一 Payroll 人员 ID 与该 `roster_id` 的关联；唯一且无已知关键冲突时自动匹配，即使考勤来源缺少公司或用工性质。岗位是软辅助字段，不单独阻断。异常候选继续走原有安全确认流程。`list_roster` 本身不返回 Payroll 人员 ID，因此不得从 `roster_id` 推测；现有候选接口仍可能执行历史证据查询，Skill 优化不代表服务端查询已减少。候选不等于可确认身份；展示完整候选信息后才接受用户明确选择。匹配不等于考勤确认或核算授权。
4. **历史工资覆盖与正式工资阶段**：只要求识别和交付考勤表的任务不得调用任何 Payroll MCP。工资流程意图明确且考勤已确认、身份映射完成后，读取 [payroll-processing.md](references/payroll-processing.md)，只读调用 `check_historical_salary_readiness` 并用 `scripts/payroll_readiness.py` 校验；默认候选仅为身份可靠且 `COVERED` 的人员。身份冲突先处理；未匹配、缺少历史、歧义、未知人员保留在排除原因中。展示月份、唯一人员范围、人数、排除事项以及正式提交/Precheck/核算的执行顺序，随后等待一次明确工资核算执行授权。通过 `PAYROLL_EXECUTION` 后，依次提交、核验提交回执、执行正式 Precheck、仅在 `valid=true` 时核算，并调用既有五 Sheet 导出器；不得自动缩围。覆盖结果、考勤或映射摘要变化、批次冲突、提交结果不明或 Precheck 阻塞时立即停止并重新核验/展示，不复用旧授权。固定 Task/Batch/Operation ID 规则不变。发现 Task ID 不构成授权；不向用户索取 Task ID 或 Batch ID。该授权是 Skills-only 的流程证据，消息来源未认证、不是 Runtime 权限；不能阻止 Agent 绕过脚本直接调用 MCP。

仅当正式 Payroll 核算结果为完整 `SUCCESS`、当前成功提交/Precheck/核算回执均已核验且 `workflow_gate.py` 的 `PAYROLL_EXPORT` 准入成功后，才调用 `scripts/build_payroll_workbook.py` 生成新的五 Sheet 工资文件。导出还必须核对原始 `get_payroll_calculation` DTO、原始 `BATCH_SNAPSHOT` 提交请求、当前 `attendance.json`、当前 `person-matches.json` 和考勤快照的逐字段内容；缺少任一来源或无法建立稳定字段对应时阻断。不得为 `PARTIAL`、失败或回执不完整的结果绕过准入或手工拼表；导出失败时不得宣称工资表已生成。仅在脚本成功后声明它返回的文件。Skills-only 内容比较不能证明本地文件确实由可信 MCP 产生。

内部识别、候选和请求/响应文件统一保存在当前任务仓库的 `.attendance-work/`，识别视图保存在 `.attendance-pages/`。不要声明这些内部文件；只声明 `考勤确认表.md` 和已成功核算并实际生成的正式工资表。Artifact 收集会排除上述两个内部目录，但不会删除其中的文件。

## 新任务识别与交付顺序

按顺序完成以下步骤；内部命令无需逐项询问用户：

1. **PDF 预处理**：每个 PDF 调用一次 `scripts/pdf_prepare.py`。脚本为每页生成低尺寸整页布局概览和 1–3 张固定、高分辨率、全宽人员行带；概览加分区总数不超过 4。清单写入视图区域和 SHA。任务已有同源清单时预处理只复用缓存，不重画。
2. **单页视觉识别**：先读取一次概览，只判断表格/列布局，不从概览录入人员或考勤值；再按清单顺序各读取一次 `row_partition`。每行只从 `core_region` 所属分区录入，裁剪重叠只用于保留完整边界行。用原表印刷行号作为 `row_index`，不得按姓名合并同名人员。
3. **逐页 JSON 持久化**：综合本页固定分区，生成一份页级 JSON，保留 `row_index`、逐日原始标记、印刷出勤和行绑定状态；有冲突或不确定时写入警告。立即调用 `attendance_store.py save-page`；成功后进入下一页。失败时使用已读取视图修正 JSON，不重读图片、不覆盖已保存页。
4. **全页完整性检查**：全部页已观察并保存后调用 `attendance_store.py status`。缺失或无效页时停止并报告，不能组装正式工作数据。
5. **汇总工作数据**：仅当全部页有效时调用 `attendance_store.py assemble` 生成 `attendance.json`。
6. **考勤核对**：调用 `attendance_review.py check`；再调用 `attendance_diagnostics.py --workdir <工作目录>` 生成内部摘要。诊断不读取 PDF 或图片，也不进入正式产物。
7. **导出核对表**：调用 `attendance_export.py` 生成 `考勤确认表.md`。保留来源矛盾、未知状态、缺日和印刷值差异，不据此推算或覆盖原始事实。
8. **声明正式产物**：考勤表导出成功后，直接调用一次 `artifact_declare`，并在该次声明中提供正式路径、标题、MIME Type、Artifact Type 和 `is_final=true`；不得先声明 `is_final=false` 再依赖 Git Diff 兜底。只有响应 `ok=true` 才表示声明成功。
9. **简短回复**：说明识别范围、核对表生成/声明状态及需要用户核实的事项，然后停止。不得为写回复重新扫描 PDF。

Skill 能约束正常流程；`save-page` 校验行索引并拒绝覆盖已保存页级 JSON。现有 Runtime 没有按图片视图强制读取次数的技术闸门。不得声称已技术性杜绝任意工具或 Shell 重读。
正常识别不调用 OCR、视觉子代理或 Agent 自行裁图/生成补充图像；只读取清单内一次性生成的固定视图。

## 核对、修改和导出

工作数据只修改当前任务的 `attendance.json`，不修改 PDF 或逐页识别快照。通过稳定 `record_id` 定位人员；姓名不能用于合并同名人员。单项或批量修改均调用 `scripts/attendance_review.py apply`，再运行 `check`。脚本校验整批后一次写入。具体状态语义、输入格式和异常规则只在进入本阶段时读取 `references/attendance-review.md`。

导出当前版本：

```sh
python3 scripts/attendance_export.py --data <工作目录>/attendance.json --output <当前项目仓库>/考勤确认表.md
```

核对表应保留必要待确认事项；缺日、未知状态、印刷值冲突、来源页警告或无法确定项目归属不得伪装成完整确定数据。原始日明细仍在 JSON 工作数据中，Markdown 只显示项目分组汇总。

诊断摘要保存在 `.attendance-work/.attendance-diagnostics.json`，仅供内部排查；不要声明为 Artifact，也不要复制到最终 Markdown 或对话回复。预处理耗时来自脚本的单调时钟；模型推理耗时和 Agent 实际图片读取次数不可观测时保持 `null`。

## 正式产物交付

仅在导出脚本成功后继续：确认其返回的绝对路径确实存在、是普通文件且位于当前项目仓库内，然后调用 Lework `artifact_declare`：

```json
{
  "path": "<导出结果中的绝对路径>",
  "title": "<例如：2026年6月考勤确认表>",
  "mime_type": "text/markdown",
  "artifact_type": "file",
  "is_final": true
}
```

只有工具成功且返回 JSON 中 `ok` 为 `true`，才能说“考勤确认表已交付”。该正式声明必须在一次调用中设置 `is_final=true`，不能依赖 Git Diff 兜底替代声明。仅当工具明确表示声明尚未写入且错误可恢复时，才可原样重试一次；结果不明确时不得重复追加声明，应报告状态待确认。路径、文件不存在、项目仓库范围等确定性错误不得重试，应报告交付未完成。没有可用的 `artifact_declare` 时报告环境阻塞，不得只报文件名并称已交付。

区分三个事实：文件生成成功、`artifact_declare` 声明成功、前端实际显示卡片。工具返回 `ok=true` 只证明声明写入成功，不证明 UI 卡片已显示；只有观察到实际 UI 证据时才能声称卡片已显示。不得修改 Lework 产品代码来补足交付。

## 面客回复

默认用简体中文，简要说明识别月份/人数/项目、核对表是否生成及是否交付成功、需要用户核实的业务事项。不要复制整张表、逐日符号、JSON、路径、脚本名或内部错误码。未成功生成核对表或未成功声明产物时，明确区分“文件未生成”与“文件已生成但交付未完成”；不声称卡片已显示。考勤表交付后等待用户自然语言核对或确认，不自动开展人员匹配和工资核算。用户确认考勤后，只有当前任务原始指令已明确要求该后续阶段时才继续身份匹配及只读覆盖检查；否则等待用户提出。人员映射完成本身仍不授权工资核算。
