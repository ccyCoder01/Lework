# 考勤核对

## 阶段路由

1. **上传与识别**：新任务首次进入时读取 [recognition.md](references/recognition.md)，按下面九步执行。每个 PDF 只做一次确定性预处理；每页按清单读取一次布局概览和每个固定数据分区，不能临时增图或补认。逐页观察后立即保存。
2. **自然语言核对与修改**：用户要求查看、修改或确认考勤时读取 [attendance-review.md](references/attendance-review.md)。Agent 将明确的自然语言更正转成脚本 JSON 请求；目标或事实有歧义时只询问必要问题。每次修改后重新检查、导出最新核对表并重新声明该文件。
3. **用户确认后的工资阶段**：只有用户明确要求开始核算后，才可进入当前已配置的身份与 Payroll 流程；不得把生成或声明考勤表理解为核算授权。Payroll 提交/计算可能写入正式业务记录，禁止称为无副作用试算。若环境未配置该能力或授权不足，说明业务阻塞，不要求用户选择内部技术方案。

## 新任务识别与交付顺序

按顺序完成以下步骤；内部命令无需逐项询问用户：

1. **PDF 预处理**：每个 PDF 调用一次 `scripts/pdf_prepare.py`。脚本为每页生成低尺寸整页布局概览和 1–3 张固定、高分辨率、全宽人员行带；概览加分区总数不超过 4。清单写入视图区域和 SHA。任务已有同源清单时预处理只复用缓存，不重画。
2. **单页视觉识别**：先读取一次概览，只判断表格/列布局，不从概览录入人员或考勤值；再按清单顺序各读取一次 `row_partition`。每行只从 `core_region` 所属分区录入，裁剪重叠只用于保留完整边界行。用原表印刷行号作为 `row_index`，不得按姓名合并同名人员。
3. **逐页 JSON 持久化**：综合本页固定分区，生成一份页级 JSON，保留 `row_index`、逐日原始标记、印刷出勤和行绑定状态；有冲突或不确定时写入警告。立即调用 `attendance_store.py save-page`；成功后进入下一页。失败时使用已读取视图修正 JSON，不重读图片、不覆盖已保存页。
4. **全页完整性检查**：全部页已观察并保存后调用 `attendance_store.py status`。缺失或无效页时停止并报告，不能组装正式工作数据。
5. **汇总工作数据**：仅当全部页有效时调用 `attendance_store.py assemble` 生成 `attendance.json`。
6. **考勤核对**：调用 `attendance_review.py check`；再调用 `attendance_diagnostics.py --workdir <工作目录>` 生成内部摘要。诊断不读取 PDF 或图片，也不进入正式产物。
7. **导出核对表**：调用 `attendance_export.py` 生成 `考勤确认表.md`。保留来源矛盾、未知状态、缺日和印刷值差异，不据此推算或覆盖原始事实。
8. **声明正式产物**：仅在文件生成且路径有效后调用 `artifact_declare`。只有响应 `ok=true` 才表示声明成功。
9. **简短回复**：说明识别范围、核对表生成/声明状态及需要用户核实的事项，然后停止。不得为写回复重新扫描 PDF。

Skill 能约束正常流程；`save-page` 校验行索引并拒绝覆盖已保存页级 JSON。现有 Runtime 没有按图片视图强制读取次数的技术闸门。不得声称已技术性杜绝任意工具或 Shell 重读。
正常识别不调用 OCR、视觉子代理或 Agent 自行裁图/生成补充图像；只读取清单内一次性生成的固定视图。

## 核对、修改和导出

工作数据只修改当前任务的 `attendance.json`，不修改 PDF 或逐页识别快照。通过稳定 `record_id` 定位人员；姓名不能用于合并同名人员。单项或批量修改均调用 `scripts/attendance_review.py apply`，再运行 `check`。脚本校验整批后一次写入。具体状态语义、输入格式和异常规则只在进入本阶段时读取 `references/attendance-review.md`。

导出当前版本：

```sh
python3 scripts/attendance_export.py --data <工作目录>/attendance.json --output <当前项目仓库>/考勤确认表.md
```

核对表应保留必要待确认事项；缺日、未知状态、印刷值冲突、来源页警告或无法确定项目归属不得伪装成完整确定数据。原始日明细仍在 JSON 工作数据中，Markdown 只显示项目分组汇总。

诊断摘要保存在工作目录的 `.attendance-diagnostics.json`，仅供内部排查；不要声明为 Artifact，也不要复制到最终 Markdown 或对话回复。预处理耗时来自脚本的单调时钟；模型推理耗时和 Agent 实际图片读取次数不可观测时保持 `null`。

## 正式产物交付

仅在导出脚本成功后继续：确认其返回的绝对路径确实存在、是普通文件且位于当前项目仓库内，然后调用 Lework `artifact_declare`：

```json
{
  "path": "<导出结果中的绝对路径>",
  "title": "<例如：2026年6月考勤确认表>",
  "mime_type": "text/markdown",
  "artifact_type": "file",
  "is_final": true
}
```

只有工具成功且返回 JSON 中 `ok` 为 `true`，才能说“考勤确认表已交付”。仅当工具明确表示声明尚未写入且错误可恢复时，才可原样重试一次；结果不明确时不得重复追加声明，应报告状态待确认。路径、文件不存在、项目仓库范围等确定性错误不得重试，应报告交付未完成。没有可用的 `artifact_declare` 时报告环境阻塞，不得只报文件名并称已交付。

区分三个事实：文件生成成功、`artifact_declare` 声明成功、前端实际显示卡片。工具返回 `ok=true` 只证明声明写入成功，不证明 UI 卡片已显示；只有观察到实际 UI 证据时才能声称卡片已显示。不得修改 Lework 产品代码来补足交付。

## 面客回复

默认用简体中文，简要说明识别月份/人数/项目、核对表是否生成及是否交付成功、需要用户核实的业务事项。不要复制整张表、逐日符号、JSON、路径、脚本名或内部错误码。未成功生成核对表或未成功声明产物时，明确区分“文件未生成”与“文件已生成但交付未完成”；不声称卡片已显示。考勤表交付后等待用户自然语言核对或确认，不自动开展人员匹配和工资核算。
